# Claude 周卡迁移与发布方案

## 基线与实际部署

当前生产是 main-server 上的 sub2api2，2026 年 10 月 19 日核验镜像 .13；历史 docs/OPERATIONS.md 含旧 BWH 和蓝绿记录，不能直接照搬为当前部署命令。

源码、镜像、数据库迁移清单和运行程序摘要必须同时核对。生产若有新发布，先取得对应提交和未提交构建改动证据，再重审本包受影响位置。不要把上游最新分支覆盖 Monas 二开。

## 结构扩展

1. 分配未使用的迁移号，增加模式字段、四张表和必要的可空关联列。
2. 原有分组全部默认 windows，不自动转换 group 6，也不自动开卡。
3. 保留原生 user_id 加 group_id 的非删除唯一约束及 carpool_billing_bindings 的主键。
4. 大表 usage_logs 的索引使用项目既有 notx 并发创建方式；外键先 NOT VALID 再单独验证。
5. 迁移设置有界 lock_timeout 和 statement_timeout；不能在高峰长时间等待表锁。
6. Ent schema 和 SQL 同步，但生产迁移由 SQL 管理，不使用 Ent 自动建表改生产。
7. 先在合成库和脱敏隔离副本验证迁移，再随 R1 发布结构。
8. 不改写历史实际费用、普通余额、拼车周期、绑定或 ledger。

取消功能的更新和流水不可变触发器必须经真实 PostgreSQL 验证；单看 SQL 文本不算执行通过。

v2 同时增加 users.claude_subscription_concurrency，保留原用户 concurrency；上线前配置明确的独立 Claude 默认上限。Claude 新 Redis scope 不搬迁或清空 GPT 键。目标 Claude 组的旧池活跃请求必须排空后才切新池，所有实例和回退镜像都须具备新 scope 识别或拒绝能力，详见 concurrency-isolation.md。

## 版本能力矩阵

| 版本 | 识别 term | 双 Key 共存 | term 生成 | 恢复 |
| --- | --- | --- | --- | --- |
| R0 当前 .13 | 否 | 否 | 不安全 | 不认识新凭据 |
| R1 兼容拒绝版 | 是 | 是 | 明确拒绝 | 保留可独立运行的兼容恢复命令或 worker |
| R2 完整实现且开关关闭 | 是 | 是 | 明确拒绝 | 是 |
| R2 启用指定组 | 是 | 是 | 完整新路径 | 是 |

R1 必须至少能解释新凭据，或携带与其同版本保证兼容的恢复组件；不能在激活后把恢复能力退掉。因此 I1 的 R1 首次构建用于前置兼容验证，I3 完成后需要产出“禁用新准入但保留恢复”的最终回退镜像并冻结摘要。此镜像才是正式发布的回退目标。

所谓“禁用功能”只关闭新手动开卡、新订单销售与新准入，不关闭已付订单履约、对账和已知请求恢复，也不把 mode 改为 windows 或 standard。

## 生产启用前

- 完成 I0 至 I5 及测试门槛，构建不可变镜像和前端。
- 保存生产最新备份并验证可读取；备份用于灾难恢复，不作为发布后覆盖当前账本的工具。
- 列出全部服务副本、实际入口、正在运行的后台 worker 和版本；只读 health 不能证明账务兼容。
- 对待切换 Claude 分组生成影响预览，包含现有 Key 的用户集合、计划开卡额度、当前普通余额请求和未完成订单。
- 用户为首批开卡对象明确给定额度；未指定额度者切换后没有使用权，不能按其普通余额自动推算。
- group 6 的账号绑定、模型白名单、0.2 倍率和代理路由单独保留快照，除业务批准外不调整。
- 验证该组没有 carpool binding；若出现异常绑定，先调查，不自动删除。

## 切换步骤

1. 所有服务实例先升级到具备最终 group 状态复核和分组在途计数的兼容候选；此时组仍是原 standard。
2. 把目标 Claude 组进入维护状态，停止新生成并失效该组 Key 缓存。准备迁移的组在旧模式阶段也受数据库最终状态检查保护，不能仅依赖 L1 TTL。
3. 等待该组已准入请求结束、用量完成结算，确认所有副本在途计数归零。超过预定排空窗口就保持维护并调查，不强杀后当作无消费。
4. 用专用管理服务执行转换事务，期间该组权益和订单写入同样受维护门禁保护。先按 user_id 顺序取得目标 user/group scope 锁，再按 parent、term 顺序创建批准的卡，最后锁组复核并切换 anthropic subscription term，写操作结果与缓存 outbox。任何集合变化或前置条件变化均中止并重做预览；完整事务边界见 integration-contracts.md。
5. 同一事务应完成相关模式和权益变化；不能先把组变成订阅、再逐条异步补卡。
6. 检查缓存失效与数据库约束，再解除维护，只允许指定组的 term 生成。
7. 验证管理员查询和用户摘要；按明确批准的测试用户执行少量生成，逐条比对新 ledger、Key 计数、usage_logs 和 GPT 无变动。
8. 持续观察错误、已知待结算、未知用量、超额、重复计费和 GPT 指标。

若现有发布设施不能只暂停 Claude 组，必须使用经过评审的现有 drain 流程并安排维护窗口，不得声称在途请求没有影响而省略排空。执行者需要给出实际停流范围和窗口，不能套用旧主机的脚本路径。

转换服务仅在首次 group mode 切换时允许批量 scope 锁，按 user_id 数字升序。普通开卡和恢复事务只锁一个 scope；严禁多用户循环中任意顺序持锁。对组6没有指定额度的历史 Key 不删除，保持身份，调用时返回无有效订阅。

## 应用回退

**首选：** 关闭 term 新准入，保留恢复与查询，退到已验证的兼容拒绝镜像。排空并结算后继续保留全部最新数据库内容。GPT 正常服务，Claude 返回维护或暂不可用。

**不支持常规直接回退 .13：** 它不理解 quota_mode，可能执行旧窗口逻辑；也会重新阻止同用户 Claude Key 与 GPT 续费共存。直接退 .13 需要额外的兼容补丁与停用措施重新验收，不能作为本计划的一键回退。

不执行 DOWN 删除新表，不恢复旧数据库盖掉发布后的账务，不把 term 组改回普通余额来恢复可用。切换过程失败且转换事务未提交时保持原数据；已提交后使用幂等结果恢复，不重新生成额度。

## 失败门槛

任一出现即停止扩大启用范围：跨来源写入、重复 debit、旧卡消费写新卡、账本不平、未知费用被写零、GPT 原功能新失败、无法确认全部实例版本、迁移锁持续超时。

自动化可以告警和拒绝启用，不应自动切换数据库、清账、重置额度或回退到余额模式。
