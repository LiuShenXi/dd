# Claude 独立周卡需求与验收

## 目标和已确认决策

用户确认管理员为每个用户开卡时独立填写额度，Claude 与 GPT 额度彻底隔离，既有拼车功能保持原行为；允许同一用户同时持有两类权益。前述方案中的七日有效期、当期额度快照和下一期独立额度作为本架构的实施口径。

本轮交付架构，开发交给 Sol。线上开卡对象、具体额度和切换时机不是本包自动决定的业务数据。

## 现状证据

生产快照中，Claude 分组 6 的平台为 anthropic、计费类型为 standard、倍率为 0.2，日周月限额为空；subscription_plans 和非删除 user_subscriptions 均无记录。GPT 拼车通过 group 2 的逐用户绑定投影成 carpool，数据库中的共享分组本身仍为 standard。

原生订阅按 user_id 加 group_id 查找，额度来自 groups。拼车绑定投影按 user_id 查询后会拒绝其他分组的 Key；开通和续费流程还要求用户所有 Key 同属 GPT 分组。因此只增加一个周额度字段无法实现双订阅共存。证据锚点见代码索引 S01 至 S12。

## 术语和金额

- 周卡：一个用户在一个 Claude 分组上的 168 小时使用额度，不是可提款余额。
- 当期额度：管理员填写或从套餐默认值复制的 USD 金额，开卡后冻结。
- 已用额度：本卡已结算费用净额。采用现有 ActualCost，保留用户分组倍率、模型价格、缓存和已有定价规则。
- 待结算费用：本卡 usage_known 的可信实际费用合计，尚未入流水；与未知费用区分。
- 剩余额度：有效期内 max(额度减已用减已知待结算, 0)；到期或取消后，对用户显示可用为零，历史未用量单独保留。
- 下一期：独立记录，不提前吸收当前卡溢出费用，不自动叠加额度。
- API Key 配额：现有 Key 自身的附加限额，不是另一份周卡，也不能增加周卡总额。
- 精度：货币入账统一使用当前 UsageBillingMonetaryScale 等于 8。新 API 金额用十进制字符串，不能用 JavaScript 浮点数计算财务结果。

## 额度耗尽的精确定义

准入事务发现当前卡 used_usd 加同卡已知待结算费用大于或等于 quota_usd 时拒绝新请求。已准入而尚未结算的请求仍按真实费用完成结算，允许 used_usd 超过 quota_usd。这延续现有后扣语义；超额是当前卡的已用量，不能形成对 GPT、普通余额或下一张卡的自动追债。当前卡有超过处理时限的未知请求需要核查时，暂停该卡新准入；恢复语义见跨模块集成契约。

首版不承诺零超额，也不能用截断实际费用或拒绝落账伪造零超额。运维记录并告警超额金额及当时在途请求数。若需要严格预付硬上限，应另行确定输入和输出计费上界、预占、释放和超额补偿协议；未完成上界证明不能把估算描述成硬限制。

## 交付范围

完整开发包含后台逐用户开卡与续卡、用户查询、三种既有 Claude HTTP 协议入口、互斥计费、恢复、对账、套餐默认额度与在线订单快照。先交付手动开卡闭环，再接在线售卖；售卖功能完成前不得为新模式上架套餐。

新模式的兑换码和依赖旧式增减天数的自动退款（全额及部分）不在首版开放。服务端必须阻止旧入口操作新模式。未使用的未来卡可通过明确取消流程撤销权益；涉及现金退款仍由独立支付退款流程处理，不能用充值普通余额替代。

不新增跨厂商钱包，不改 GPT 商品价格，不改代理或上游凭据，不重写现有拼车流水，不为用户自动生成或迁移 Key。
