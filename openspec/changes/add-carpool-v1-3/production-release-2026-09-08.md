## 1. 已确认的业务规则

- 纳入本次迁移的存量用户，订阅开始时间取原始 `users.created_at`，一般规则是该时间加 28 × 24 小时；用户已确认名单中两个“550 一周”账号为 7 × 24 小时有效期，是 28 天规则的明确例外。保留秒和小数秒，不按自然月、零点或发版时间重算。
- 本轮迁移不得改写用户现有余额。正常请求的扣费仍继续；不能把“迁移只读”实现为全库余额冻结。
- 用户已确认全部余额都是订阅套餐内额度，不存在独立现金充值；加油为新功能，所有迁移用户 `boost_used=0`。管理员不建立订阅权益。
- 上述订阅余额接管规则仅适用于名单中的 20 位订阅用户。用户已确认另外 3 个账号为注册未开通，排除迁移并保留原状。管理员继续使用可手工调整的普通余额，不开通订阅；原有 2 把 Key 的 ID、密钥值、状态和分组关联全部保留，不删除、不重建、不轮换，不改管理员余额。
- 统一周期锚点为 `2026-09-08T09:40:16+08:00`，对应 UTC `2026-09-08T01:40:16Z`。该时间是用户已执行重置的时间，不是待执行的重置指令。
- 在 2026-09-15 09:40:16 之前迁移、且未提前到期的用户，当前周期为 `[2026-09-08 09:40:16, 2026-09-15 09:40:16)`。周期结束不得超过个人订阅到期时间。
- 自然补满、后续特殊重置均不得延长个人已确认的订阅期限。迁移不得再执行官方全局重置、首次满额赠送或补发历史额度；加油已用次数为 0 不代表发布时自动发放加油额度。
- 目标是地址、API Key、登录态保持可用，正在生成的请求正常完成，余额不因迁移跳变。不能承诺任意长连接下零等待、零重连且固定时间内完成切换。

## 3. 金额接管与守恒

现有生产通过 `users.balance` 计费，新拼车通过周期的 base / boost / manual 及流水计费。两者不是同一余额字段。因此只插入订阅日期不会自动完成计费切换。

建议的业务接管方式：在所有旧账请求结算完成的边界 C，只读取得每人的真实剩余额度 B，将 B 作为新拼车账本的期初余额；原 `users.balance` 原样保留。迁移本身不扣、不清零、不补满该字段。迁移完成后，该份已经接管的权益只允许经拼车账本消费；重新创建原分组 Key 仍必须遵循个人计费绑定，不能通过旧余额入口、跨分组回退或提现接口重复支用。

用户已确认 20 位订阅用户原余额全部代表本次订阅套餐权益，无需拆分独立现金余额。接管当前剩额为基础额度期初值，历史加油余额为 0；不得因上线新加油功能自动发放额度。档位以已提供名单为依据；另外 3 个注册未开通账号与管理员均排除，不由余额反推或自动开通。

必须满足：

```text
迁移事务前 users.balance = 迁移事务后 users.balance
新周期期初净额 = 接管边界 C 的已确认剩余额度 B
期初流水净额 = base + boost + manual
迁移造成的总可花额度增量 = 0
每个真实使用请求只结算一次，且明确归属旧账或新账
```

对迁移身份使用最小数据库权限：只允许 SELECT 用户余额及写入指定拼车、迁移状态、关联字段，不能拥有修改余额的权限；不能给迁移脚本直接使用可绕过限制的业务数据库所有者权限。正常业务进程保留必要扣费权限。名单和金额快照放权限受控、Git 外位置，不进入公开文档。

不以“发版前后全库余额完全相等”验收在线系统，期间正常消费会改变余额。应在接入屏障生效、旧结算完成后的同一事务核对不变量，并用真实流水解释窗口内的正常差额。

## 4. 日期和存量记录

| 字段或记录 | 迁移规则 |
| --- | --- |
| 原始注册时间 | 只读原字段，不修改 `users.created_at` |
| 会员期限 | `starts_at = users.created_at`；一般为 `starts_at + 28 days`，两个“一周”条目为 `starts_at + 7 days` |
| 当前周期 | 从锚点开始，截止 `min(锚点 + 7 days, expires_at)` |
| 实际接管时间 | 独立记录 `imported_at / cutover_at = C`，不伪装成 09:40:16 时已建立新账本 |
| 套餐 | 来自确认过的用户到套餐映射和冻结快照；禁止由剩余余额反推 |
| 加油 | 用户已确认是新功能：`boost_used=0`，加油余额为 0，不自动领取 |
| 历史使用 | 保留旧使用日志；无法完整证明时 `history_complete=false`，新账统计起点为 C |
| 09:40:16 重置 | 记录为用户确认的历史锚点及来源说明，不调用会发钱或通知的重置执行器 |

统一锚点与注册时间是两套时间，不能用改注册时间来迁就周期算法。跨过统一周边界才发版时，先停下重算预览，并明确新的当前周期；不能导入已经过期的 active 周期或自动追补遗漏周期。

执行前若新增重置后注册账号，其周期不能早于订阅开始，必须单列规则；若有已过个人有效期的账号，应如实列为到期，不能悄悄续期，也不能把“到期拒绝”误判成切流故障。当前只读快照没有已过 28 天或重置后注册的账号。两个“一周”条目已确认为 7 天有效期：账号 ID 11 到期于北京时间 `2026-09-11 21:16:25.886623`，账号 ID 12 到期于 `2026-09-11 21:18:57.818754`。当前周期从统一锚点开始、至各自到期时结束，不会等到 9 月 15 日再补满。现有 7 天套餐快照默认 fixed，独立锚点导入还必须覆盖这一兼容路径。

## 5. 已闭合的实现缺口

1. 独立接管周期：新增 `BuildCarpoolTakeoverCycles` 与明确的当前周期起点，保留注册时间、微秒和个人到期边界；特殊额度及有效期冻结在个人套餐快照中，默认续费继承。
2. 迁移 CLI：支持 schema、preview、apply、verify；名单和批次指纹校验、行锁下读取实际余额、幂等提交及受保护字段摘要。迁移角色没有 `UPDATE users.balance` 权限。
3. 接入屏障：覆盖 HTTP、完整 SSE/WS 生命周期和延迟用量队列；另查冻结金额、持久图片及支付工作。锁定后核验不明确时保持暂停，严格缓存刷新成功才恢复。
4. 发布控制：`RELEASE_DRAIN_START_HELD` 支持重启后保持迁移态；`CARPOOL_BACKGROUND_ENABLED=false` 禁止迁移实例提前维护周期或观察重置。完成账本切换后才启动正式维护实例。
5. 关停：实际使用只重载 Nginx 的切槽脚本，旧 worker 和连接自然排空后才正常停止容器；核验用量池与基础设施清理日志。不执行有强制排空截止时间的旧部署入口。

## 6. 建议发布顺序

### A. 锁版本与只读预演

- 以生产 `36266f512776` 为基线审计全部待发布提交、今天未提交修改、新文件及迁移 235 至 243，锁定唯一提交与镜像 digest。最终范围按真实差异确认，不只看本轮编辑文件。
- 当前提示词风控目录标记为设计提案，不能计作已完成、已启用的发版功能。
- 生成完整迁移预览：用户 ID、套餐、注册/到期时间、周期起止、余额来源与分桶、加油次数、可迁移/待确认原因、批次幂等键。每个账号都有结果。
- 再次核验正式路由、文件 active-slot、镜像、schema checksum、共享数据卷、数据库版本、磁盘/内存、JWT/会话密钥及 Redis 连接。

### B. 生产结构副本演练

- 从执行前的新快照建立独立、脱敏且禁止外发的环境；不用现有测试库覆盖生产，也不用测试用户、Key 或测试套餐数据覆盖生产。
- 对最终镜像执行真实 SQL 升级、迁移 dry-run、重复执行及事务中断恢复；特别测试标准计费到拼车计费的切换。
- 逐条评估待执行 DDL 的锁和耗时，设置锁等待上限；超时中止，避免 `usage_logs` 等热表长时间阻塞。迁移串行锁不能替代在线 DDL 评估。
- 验证旧版在扩展后的结构上仍能启动/计费，准备经验证的备份恢复与兼容回滚镜像。备份在另一隔离库试恢复，不只检查文件存在。

### C. 先上线程序，维持原计费

- 获取发布锁，保存生产备份、现有路由/配置和镜像身份；新包只部署到正式备用槽，接生产现有 PostgreSQL/Redis/会话配置，不搬动生产数据库。
- 先执行经过审查的兼容结构升级；新实例以受控 staging 状态预热。新表为空或记录尚未激活时，不能触发业务补满或公告。
- 保持分组 2 为 standard，保持原 Key 内容和 URL；先让新程序承接原账本请求。公网入口及内部 `sub2api:8080` 均由稳定路由切换，核对不存在直连旧容器的入口。
- 预先创建兼容的个人计费绑定表；空表时全员维持原账本。分组 2 始终为 standard，所有 Key 和路由关联不变。
- Nginx reload 后，旧请求留在 green 正常完成；禁止因 15 分钟到时直接停止旧容器。等所有旧流量、持久任务和未结算工作完成；长 WS 若无法自然结束，延后账本切换，不宣称此时已完成迁移。
- 旧版本实例退出服务和后台任务所有权后，才允许执行 D。共享应用目录、旧前端动态 chunk、签名密钥和会话兼容性一并验证，避免已打开页面切流后 404 或登出。

### D. 再切换账本

- 先在线观察旧账任务接近清空。在唯一新版本上启用覆盖目标用户全部财务入口的接入屏障，短暂排队新请求，不关闭正在响应的流。
- 屏障是必须新增并验证的能力。建议排队预算先按不超过 5 秒设计，并在演练中验证客户端超时；若旧请求/异步结算未清空，取消本次尝试、释放队列继续旧模式，不取过早余额、不强制断流。
- 无目标用户旧账未结算请求后，在受控事务中锁定目标记录，读取即时 B，登记会员/当前周期/期初流水/个人计费绑定/批次状态，限定 20 位成员允许使用的分组，验证余额、分组及全部 Key 行未变。绑定和会员必须同时提交，不能暴露绑定已切换而会员尚未登记的中间状态。管理员 Key ID 2、6 不迁移、不删除、不重建，管理员继续 standard 计费，不能将其正常扣费误计为迁移改余额。
- 事务提交前失败则全部回滚。相同批次重试只返回原结果，不能再建会员、再写期初流水或再次改变周期。
- 提交后，屏障下定向刷新所有应用实例的 Key/用户/分组鉴权缓存及相关计费缓存；请求最终准入必须以权威迁移状态决定账本，缓存清理不能作为唯一正确性保障。不能全库清空 Redis 或并发计数。
- 只有确认新计费链路可用后才释放排队请求并接管周期维护。缓存更新失败时保持受控状态并重试，不能释放请求到旧账路径。
- 本方案优先使用一个完整账本切换边界；若业务必须持续高负载下零排队，应另做按用户切换及跨账延迟结算协议，开发成本显著更高，不能由改部署脚本替代。
